# CI Cook Wiring — Design Spec (Track 5)

- **Date:** 2026-06-22
- **Scope:** Wire the real content-addressed cooker (`pipeline/cook.py`) into CI as a first-class, **warm-cacheable** build stage, gate the cooker tests, and surface cook metrics on the dashboard.
- **Status:** Design approved (all 5 sections), pending spec review → implementation plan.
- **Track:** R&D / Track 5 (pipeline). Deferred from the Phase-2 heavy-run prep campaign (`2026-06-21-heavy-run-prep-design.md` §3.3) as a feature, not prep.
- **Operating principle (lab):** ship a **demoable artifact**. Here that is: a CI stage that cooks real synthetic game assets into a content-addressed `.pak`, *reuses an unchanged asset across builds* (visible cache-hit semantics), gates the cooker against regressions, and renders cook metrics next to the build metrics.

## 1. Goal / win-condition

A new TeamCity stage runs the real cooker in CI, persists its content-addressed store (CAS) across builds so a re-cook of unchanged assets is a cache hit, the 42 cooker unit tests gate every push, and the dashboard shows a "Cook (Track 5)" panel.

**Demoable artifact:** point at three things — (1) the `Cook Assets` stage publishing a real `Cooked-assets.pak` + `manifest.toc.json`; (2) a warm build reporting `cooked 0 / cached 8` (and a one-asset edit → partial recook); (3) the dashboard cook panel + a green `pipeline-cooker` CI check.

**Honesty note (do not oversell):** at this asset scale (4 textures, 2 audio, 2 characters) the cook is sub-second, so the warm-vs-cold *wall-clock* delta is tiny. The demo signal is the **cache-hit semantics** (`cooked N / cached M`, `--dry-run` "nothing would recook"), i.e. the mechanism — not a dramatic time number.

## 2. Background / current state (ground truth, 2026-06-22)

- **Cook Data stage** (`AAASandbox_CookData` in `ci/scripts/bootstrap-builds.ps1`) runs the **toy** C++ `hoops_cooker Data Cooked.pak`, which concatenates `hoops-brawl-seed/Data/*.txt` into `Cooked.pak` (16-byte header, no TOC). It is part of the **hoops-brawl-seed sample pipeline**: `Compile → (Smoke Test ∥ Cook Data) → Package`, where Package bundles `Cooked.pak` into the tarball.
- **Real cooker** (`pipeline/cook.py`) is content-addressed: cooks **synthetic textures/audio/characters** from `pipeline/assets/` (generated by `pipeline/scripts/make-samples.py`) into a `pipeline/cooked/` CAS + `manifest.toc.json`; `--pack out.pak` emits a single deterministic ZIP `.pak`; `--stats-json` writes run stats; `--dry-run` reports would-recook. 42 unit tests green. The toy and real cookers cook **different asset sets** — the real cooker is **not** a drop-in for the toy.
- **Agent image** (`ci/agent/Dockerfile`) already has python3 + Pillow + p4 + C++ toolchain. Its own comment already names the intent to run `pipeline/cook.py`; only the stage wiring is missing.
- **Inputs are deterministic** — `make-samples.py` docstring: "deterministic, no randomness." Gradient PNGs + sine WAVs + fixed character JSON ⇒ byte-identical inputs across runs ⇒ stable cook-keys ⇒ warm-cache **can** hit.
- **Two build agents** — `agent-linux-01`, `agent-linux-02` (distinct compose services, separate conf volumes). The hoops chain fans out so leaves run on different agents. An **agent-local** cache would warm unreliably across two agents — decisive for choosing the artifact-dependency cache.
- **GitHub Actions test CI** (added by PR #1, `.github/workflows/tests.yml`) runs perforce, hoops C++, and dashboard jobs but **no `pipeline/cooker` job** — the 42 cooker tests are ungated. Gap this spec closes.
- **Dashboard** (`dashboard/`) builds `data/snapshot.json` section-per-feed: `ci` (TeamCity REST), `accel`/`unreal` (local `*.metrics/*.json` → pure transform → section), each with stale-fallback via `Merge-Feed`. Cook stats fit this as a new `pipeline` feed.

## 3. Architecture

The new stage is **additive and independent of the hoops C++ build** (the real cooker is pure Python + Pillow):

```
        Compile ──┬─> Smoke Test ─┐
                  └─> Cook Data ──┴─> Package      (hoops-brawl-seed — UNCHANGED)

        Cook Assets ⭯  (self artifact-dep on own last successful build)   (NEW, standalone)
```

**`Cook Assets` (`AAASandbox_CookAssets`)** — one config, **no** snapshot/artifact dep on Compile. Steps:
1. `python3 pipeline/scripts/make-samples.py` — regenerate `pipeline/assets/` (gitignored, deterministic).
2. `python3 pipeline/cook.py --pack Cooked-assets.pak --stats-json pipeline/.metrics/cook-%build.number%.json` — cook incrementally into `pipeline/cooked/` (the CAS unpacked from the prior build), emit the `.pak` + stats.

**Warm-cache mechanism (Approach A — artifact-dependency cache):** the config takes an **artifact dependency on itself**, source = *last successful build*, rule `cooked.zip!** => pipeline/cooked`. Each run starts with the previous run's CAS unpacked in place, cooks incrementally, then **re-publishes** `pipeline/cooked` (zipped) plus the pak/toc/stats. First-ever build has no prior artifact → cold full cook (empty-cache case, not an error).

**Why standalone, not parallel-under-Compile:** the real cooker shares nothing with the hoops C++ toolchain; coupling to Compile would add a false dependency and serialize the cook behind a C++ build it does not need. As its own root config it runs on either agent off the same VCS root.

**Why artifact-dependency over a shared Docker volume or agent-local dir:** with two agents, the cache must travel with the build, not live on one agent. The artifact-dep cache is cross-agent safe, reproducible, and **inspectable** (the CAS is a visible build artifact — good for the demo). A shared-volume "CI DDC" is a tempting nod to a real shared-DDC but trades inspectability for infra not needed yet (it is already parked as a separate Zen/DDC seed).

## 5. Data flow

**Warm-cache cycle (per `Cook Assets` build):**
```
1. TeamCity pulls artifact-dep: cooked.zip from THIS config's last successful build
   → unzips to pipeline/cooked/   (empty on the first-ever build = cold start)
2. Step 1: make-samples.py        → regenerates pipeline/assets/ (deterministic, byte-identical)
3. Step 2: cook.py --pack …       → reads pipeline/cooked/ index, hashes each asset's cook-key,
                                     recooks ONLY misses, reuses hits → prints "cooked N / cached M"
4. TeamCity publishes artifacts:  pipeline/cooked → cooked.zip   (the warmed CAS, for next run)
                                  Cooked-assets.pak, manifest.toc.json, cook-stats json
```
- **Cold run** (build #1, or after `--force`): inputs unseen → `cooked 8 / cached 0`.
- **Warm run** (build #2, unchanged source): cook-keys all match the unzipped CAS → `cooked 0 / cached 8`. ← payoff signal.
- **Partial run** (one asset changed, e.g. a texture's base RGB edited): only that asset + its dependents recook → `cooked 2 / cached 6`. ← content-addressed incrementality via the dep-edges in the `.toc`.

**Stats flow to dashboard (offline path, mirroring `unreal`):**
```
cook.py --stats-json pipeline/.metrics/cook-<id>.json
   → collect-metrics.ps1 Get-PipelineFeed reads pipeline/.metrics/*.json
   → ConvertFrom-PipelineMetrics (pure transform) → snapshot.json "pipeline" section
   → build-dashboard.ps1 renders the "Cook (Track 5)" panel
```
The committed `snapshot.json` carries the latest cook stats; stale-fallback via `Merge-Feed` keeps the section when no fresh metric exists.

**Scope line (offline vs live):** the `pipeline` section is fed from **local** `--stats-json` emits (run on the dev box, or the CI artifact copied in) — exactly as `unreal`/`accel` work today — **not** auto-pulled from TeamCity REST. Auto-pulling cook stats from the build artifact via REST is a clean follow-up, not v1 (keeps v1 off live-infra coupling, consistent with the offline-authorable ethos).

## 6. Error handling & edge cases

| Case | Handling |
|---|---|
| **Cache index must survive the artifact round-trip** ⚠️ | **The warm-cache hinges entirely on `cooked/.cookindex.json` (a dotfile) round-tripping through the artifact.** Verified offline: with all blobs present but the index removed, the cook goes **fully cold** (`cooked 8 / cached 0`) — and the build still passes, so the failure is *silent*. **Chosen mitigation (decided 2026-06-22):** (a) publish with the **directory-form** rule `pipeline/cooked => cooked.zip` (archives the dir incl. dotfiles) rather than a `pipeline/cooked/** => …` glob that may skip dotfiles; **and** (b) a **CI guard** asserting build #2 reports `cached > 0`, so a cold-cache regression fails loudly. **Not chosen:** de-dotting the index (`.cookindex.json` → `cookindex.json`) — rejected to avoid churn in `cooker/cache.py` + tests; the guard catches any cold-cache regression loudly regardless, so the dotfile stays. |
| **First-ever build (empty cache)** | No prior successful build ⇒ no `cooked.zip`. (a) Configure the self artifact-dep so a **missing source build is non-fatal** (not the TeamCity default — would otherwise fail "no suitable build found"). (b) `cook.py` `run()` already `os.makedirs(out_dir)`, so an absent/empty `pipeline/cooked/` is a clean cold start (verified). To validate in the gated live run. |
| **Corrupt / partial CAS** | **Already handled (verified):** `cache.cook_or_reuse` only counts a HIT when the index entry's backing blob exists on disk, so a missing/truncated blob is treated as a **cache miss → recook**, never a crash. Needs only a **regression test** to lock the behavior — no hardening. |
| **Determinism drift** | If make-samples or the pak/blob writes go nondeterministic (timestamps, dict order), warm-cache silently never hits (`cached 0` forever). Guard: a **regression test** asserting two consecutive cooks of identical input ⇒ `cached == total`. |
| **Unbounded CAS growth** | Content-addressed store only grows; changed assets leave orphaned blobs in `cooked.zip`. Negligible at this scale. v1 leans on TeamCity artifact-cleanup policy; a **CAS GC (prune blobs absent from the current `.toc`) is an explicit non-goal / follow-up.** |
| **Concurrent Cook Assets builds** | Both pull the same lastSuccessful CAS, each cooks in its own checkout, last-writer-wins on the published artifact — **no corruption** (the reason Approach A beats a shared volume). |
| **Empty dashboard feed** | `pipeline/.metrics/` empty ⇒ `Get-PipelineFeed` returns null ⇒ `Merge-Feed` keeps prior section (or none); render no-ops a missing `pipeline` section, like the other feeds. |

The first-build artifact-dep behavior is the one genuine TeamCity-semantics risk; everything else is small/local.

## 7. Testing

**Layers (TDD where new):**
- **Cooker units (existing 42)** — wired into the GH Actions `pipeline-cooker` job + `run-tests.sh`.
- **New: determinism regression** — two consecutive cooks of identical input ⇒ `cached == total`.
- **New: cold-start / missing-blob** — empty CAS cooks clean; a `.toc` entry with no backing blob recooks instead of crashing.
- **New: dashboard transform** — `ConvertFrom-PipelineMetrics` pure-function cases, fixture-driven.
- **New: dashboard render** — `build-dashboard.Tests.ps1` cases for the cook panel.
- **New: stage-shape assertion** — unit-assert the `AAASandbox_CookAssets` config object in `bootstrap-builds.ps1` has the right steps/artifact rules (pure data, no live server).

**Offline-verifiable in this cycle (the deliverable):**
- All unit/transform/render tests green.
- `make-samples → cook --pack --stats-json` produces the expected `.pak`/`.toc`/stats locally.
- **Local warm-cache proof**: cook twice (cold→warm) ⇒ `cached == total`; perturb one texture ⇒ partial recook — proves the cooker side with **no TeamCity needed**.
- GH Actions YAML valid + cooker job defined; dashboard renders the panel from a fixture snapshot.

**Pre-validated offline (2026-06-22, before plan — Python 3.13 / Pillow 12.1):**
- Cold cook ⇒ `cooked 8 / cached 0`; warm re-cook (unchanged) ⇒ `cooked 0 / cached 8`. **Warm-cache premise confirmed.**
- Perturb one texture (`hero_normal`) ⇒ `cooked 2 / cached 6`, recooking exactly the dependent character — dep-edge propagation confirmed.
- Two `--pack` runs of identical input ⇒ byte-identical `.pak` (sha256 match) — determinism confirmed.
- Removing `.cookindex.json` (blobs intact) ⇒ fully cold — motivates the index-survival invariant in §6.
- `--stats-json` to a non-existent dir ⇒ `FileNotFoundError` — motivates the `cook.py` makedirs fix in §4.

## 9. Success criterion / non-goals

- **Success:** every component in §4 is committed and (where offline-runnable) verified green; the local warm-cache proof passes; opening the next heavy/CI session means running the gated §8 wiring validation, nothing else.
- **Non-goals:** no change to the hoops-brawl-seed pipeline (Cook Data, the toy cooker, Package stay as-is); no CAS garbage collection; no TeamCity-REST auto-pull of cook stats into the dashboard (local-file feed only); no shared-volume "CI DDC" (parked as a separate Zen/DDC seed); no new cooker asset types or `cook.py` flag changes.
